# 多角色评审规范

对**合入候选**（PR / 功能切片 / 代码改动）做多角色评审。**只评审、不修改代码**；发现缺工具或需开发才能达标的项，列入「工具/排期开发建议」由主会话排期。

## 角色与评审维度

依次以五个角色视角评审同一改动，分别产出发现：

### 1. 程序健壮性（correctness & robustness）
- 错误处理是否完备：nil 检查、输入校验、错误前缀与可定位性（索引/上下文）
- 边界：空输入、零值、极端值（0、负、NaN/Inf、超长）、并发/竞态、panic 面
- 资源：连接/文件/锁是否释放（defer）、context 是否贯穿
- 数据一致性：事务边界、部分失败处理

### 2. 鲁棒性与容灾（resilience & disaster recovery）
- 依赖故障：DB/网络/外部源不可用时的行为（报错清晰、不 panic、可重试）
- 重试与超时：`-every` 循环失败容忍、HTTP 客户端超时、退避
- 崩溃恢复：进程中断（SIGINT）优雅退出、半写状态可恢复性（事务/ON CONFLICT）
- 可观测：失败是否留痕（日志/status/错误输出）、运维能否定位

### 3. API 兼容性（API compatibility）
- 接口签名/行为变化的影响面：仓库内所有调用点、导出符号、CLI flags、HTTP 契约（`doc/API.md`）、JSON 字段
- 向后兼容：默认值语义、零值行为、旧命令/旧参数是否仍工作
- 契约漂移：实现与文档（doc/API.md、help 文本、usage）是否一致

### 4. 产品白盒体验（product white-box UX）
- 端到端流程：安装/构建 → 运行 → 看结果，是否顺畅闭环（含 smoke/示例命令）
- 输出可读性：CLI 输出格式、帮助文本、错误信息是否可操作（告诉用户「怎么修」而非只报错）
- 是否符合预期：对照任务记录 Goal/验收逐条核对

### 5. API 调用方视角（consumer readiness）
- **判定是否达到「可使用阶段」**：验收是否全部满足、文档是否齐、有无阻塞使用的缺口
- 若未达到：站在**调用方**（外部程序/脚本/前端/其他包）角度列出缺口——契约不明确、错误语义含糊、缺示例、参数/响应不符合消费习惯、认证/边界未定义等
- 若已达到：给出「可使用」结论与最短上手路径

## 评审流程

1. 读任务记录（`doc/tasks/` 对应文件）确认 Goal/验收；**若无对应任务记录**（纯文档/配置类改动常见），标注「未找到任务记录」，依 PR 描述/commit message 推导 Goal 并照常产出
2. 读改动 diff（`git diff` / PR diff）与相关代码、契约文档（doc/API.md、doc/BACKTEST.md、doc/DATA_PIPELINE.md）
3. 必要时跑验证（`go test`、`scripts/verify.sh`、CLI 冒烟）——只读执行，不改代码
4. 按五角色逐一产出发现，最后汇总

## 输出格式（结构化报告）

```
## 评审对象
（commit/PR/范围 + 任务记录）

## 结论
- 是否达到可使用阶段: 是 / 否（原因）
- 是否建议合入: 是 / 否 / 有条件（列条件）

## 各角色发现
### 1 程序健壮性
- [严重度] 文件:行 问题 → 建议
### 2 鲁棒性与容灾
...
### 3 API 兼容性
...
### 4 产品白盒体验
...
### 5 API 调用方视角
- 可使用阶段判定与缺口清单（未达到时逐条列出调用方视角缺口）

## 工具/排期开发建议
（评审中发现缺工具、脚手架、测试设施才能达标的项，按优先级列出，供主会话排期）
```

严重度分级：`P0` 阻断合入（必须修）；`P1` 应修（合入前或紧随）；`P2` 建议（可排期）；`P3` 观察（记录即可）。

## 约束

- 只评审不修改；发现用「文件:行 + 问题 + 建议」格式，不贴大段原文。
- 报告必须真实：验证过的写「已验证」，没跑的说「未验证」，不虚构结果。
- 不评审 `doc/tasks/` 记录本身（那是元数据），只评审代码/配置/契约。
